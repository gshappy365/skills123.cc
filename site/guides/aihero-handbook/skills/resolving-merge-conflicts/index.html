/resolving-merge-conflicts 技能

逐个解决合并或变基冲突中的代码块。

已归档。 该技能在 v1.3.0 版本中已从插件中移除，不再维护。没有替代品：agent 在处理合并或变基（rebase）冲突时不需要专门的技能。本页面仅作参考保留。

resolving-merge-conflicts 逐个代码块（hunk）地处理进行中的 git 合并或变基，然后运行项目自身的检查，并以一次提交（commit）完成整个操作。

它拒绝把冲突当作单纯的文本问题来处理。在动手修改任何代码块之前，它会先把两侧的代码各自追溯到其主要来源（primary source）（提交信息、PR、原始 issue），这样它是在两个意图之间做选择，而不是在两段文本之间做选择；只要两个意图兼容，它就会同时保留两者。如果确实无法兼容，它会选择符合本次合并既定目标的那一侧，并明确指出取舍。它不会发明新行为来掩盖冲突，也从不使用 --abort。它总是把合并进行到一次完成的提交。

输入 /resolving-merge-conflicts，或者当任务匹配时，agent（智能体）会自动调用它。

当 git 已经因为冲突而停下且无法自行解决时，就轮到它出场。它的作用范围仅限于眼前这个冲突，不涉及冲突两侧的任何内容：

你的情况 技能
合并或变基进行中，工作区里有冲突标记 这个
合并已完成，但有些东西莫名出问题 diagnosing-bugs
计划如何切分工作以减少分支冲突 都不是：参见下文关于并行工作的问题

这个技能存在的意义就是防止"靠 flag 解决冲突"：用 --ours、--theirs，或者手动删掉看起来不重要的那个代码块，让冲突标记消失、构建能编译通过。这种解决方式在语法上可以完美无缺，却仍然会悄悄丢掉别人有意做出的修改。

没有读过意图，就无法保留意图。所以工作从历史开始（提交、PR、工单（ticket）），然后才转向 diff。检查步骤的存在也是出于同样的原因。该技能会找到仓库自己的自动化检查（automated check）并在提交之前运行它们，因为在 git 中，合并是最容易产出"同时满足两个分支却通不过任何一方测试"的代码的地方。

Claude Code 自己解决冲突已经相当不错了，为什么还需要一个技能？

附加价值在于"找到主要来源"和"运行反馈循环"这两个步骤，否则你每次都得手动去提示。没有提示的 agent 通常只凭 diff 就产出一个看似合理的解决方案，然后就到此为止。这个技能的价值正是它不允许 agent 跳过的那两步：阅读每一侧存在的理由，以及之后运行检查。相比一个优秀的模型（model），这只是很小的增益——而这正是设计意图。至少有一位读者预言，随着模型能力的提升，这个完整的技能终将变成无用之功。

我应该从一开始就让并行 agent 不碰相同的文件，以避免冲突吗？

多数情况下不必。在并行任务之间划分文件边界，付出的成本高于节省的成本，因为 agent 处理合并冲突的能力已经足够好，这种权衡没有表面看起来那么严苛。唯一值得保留的纪律是：先做大重构。一个大型重命名如果在十个分支已经从它分叉出来之后才落地，那种情况的成本会一直居高不下。

一个来自用户关于并行 worktree 报告的注意事项：当兄弟会话（session）各自在自己的工作区里完成一个工单时，合并回来最好由写下改动的那次会话来做，因为它已经了解意图。如果最后由一个 agent 解决所有人的冲突，它就丢失了这个技能第 2 步必须重新构建的上下文（context）。

为什么从不使用 --abort？

中止会丢掉已经完成的解决工作，并让你在下次重试时面对一模一样的冲突。这个技能是为"合并注定要发生"的场景编写的。如果你决定不该发生这次合并，那是调用之前就该做的决定，而不是循环内部的分支。

  • agent 在解决冲突时会向你引用提交信息、PR 或 issue，而不只是 diff 代码块。
  • 每个代码块最终要么保留了两侧的行为，要么带有明确说明，指出丢掉了什么以及为什么。
  • 结果中不会出现两个分支上都没有的东西。
  • agent 找到了 typecheck、测试和格式化工具，并在提交_之前_让它们全部跑绿，而不是等你发现东西坏了之后。
  • 你最终得到一个干净的工作区，操作全部完成——包括多提交变基中剩余的每一次提交。

一个随时可调用、不依赖任何其他技能的独立技能：git 卡住时启动，工作区干净并完成提交时结束。它唯一真正的邻居是 diagnosing-bugs，后者在合并顺利完成但合并后的代码出问题时接手：那是诊断问题，不是冲突问题。它不在主要的"从想法到交付"流程之内，所以 ask-matt 是了解它前后运行什么的地图。
