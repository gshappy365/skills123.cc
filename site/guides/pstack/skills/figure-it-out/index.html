/pstack:figure-it-out

自动调用

一句话现成的 23 种做法都不合适时，它现场设计一套，每步都能回头查。

什么时候用
很大的活、没有现成做法的活，或你要离开、回来再审的活。
这样说
/pstack:figure-it-out 把所有调用方从同步 store 迁到新的异步 store，行为完全不变。

用它和不用它

同一件事，直接跟 AI 说，和点名用 /pstack:figure-it-out，AI 的做法不一样：

直接说用 /pstack:figure-it-out
拿到大任务就直接开写代码先交一份阶段清单，写明怎样算做完和多严格
看自己的汇报就说做好了检查真正做出来的东西，结论标成 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE
全部做完才统一检查一遍每一小步改完就对照标准测一次，没进展就撤回

文档写了什么

原文分 6 节，约 600 个英文单词，中文译文约 1050 字，读完约 3 分钟。点一节直接跳到全文。

开头说明没有现成做法时先设计一套流程，严格程度跟着任务走，用科学方法做，留下你回来能查的决策记录。

  1. 1开始待办清单第一条是读 poteto-mode 的 Principles 部分，后面再加各个阶段。
  2. 2阶段 A：框定开跑前写清能被证伪的完成标准、量化的范围和严格程度，长任务先给你看一次。
  3. 3阶段 B：设计工作流程拆成能单独合并的小块，最没把握的先做，先搭验证工具记下改前数值，把阶段清单写下来。
  4. 4阶段 C：跑循环每块当一次实验：说出假设，做最小改动，对照标准测量，有进展就留，没进展就撤回。
  5. 5阶段 D：留下审查记录用 show-me-your-work 边做边记日志，每完成一步记一行，通常连同代码一起提交。
  6. 6阶段 E：验证并交回在真实产品上对照完成标准检查，把反复出现的纠正写成检查或脚本，再交上流程和未完成的事。

写法亮点

挑了几句原文：每句让 AI 做什么、为什么这样写管用、你写提示词时怎么借来用。

  1. 把「认真点」换成具体检查

    Rigor is gates and artifacts, not "try harder".

    严格程度是关卡和能拿来检查的东西，不是「更努力一点」。

    让 AI
    要求严格时，它会多设几道检查、多留几样证据，而不是嘴上说会更仔细。
    为什么管用
    「更努力」没法检查，「多一道关卡」做没做一眼就能看出来。
    借来用
    想让 AI 小心时写成动作：「每改一个文件就跑一次测试，并把结果贴出来。」

  2. 规定先做最没底的

    Sequence riskiest-unknown-first.

    最没把握、风险最大的排在最前。

    让 AI
    最可能卡住的部分最先做，问题早早暴露，不会做到最后才发现走不通。
    为什么管用
    一句排序规则就替 AI 定了从哪下手，它不会先挑简单的做来显得有进展。
    借来用
    交代大任务时加一句：「先做你最没把握的那一步，熟悉的放后面。」

  3. 提醒它怀疑好消息

    When something passes too easily, suspect the observation method before the system.

    某件事通过得太容易时，先怀疑观察的方法，再怀疑系统。

    让 AI
    结果好得出奇时，它先查是不是检查方法出了问题，不急着报喜。
    为什么管用
    预先说出最容易上当的那种情况，AI 真遇到时就会停下来多看一眼。
    借来用
    让 AI 跑测试时补一句：「如果一次就全部通过，先确认测试真的跑了。」

  4. 先判好灰色地带算哪边

    Inconclusive is not a pass.

    说不准不算通过。

    让 AI
    说不准的结果，它会老实报「说不准」，不会当成通过往上交。
    为什么管用
    把最容易被往好处说的情况提前判定，AI 就没法把它凑成好消息。
    借来用
    给标准时把中间情况也说清：「没跑到的测试算失败，不算通过。」

全文

descriptionDesign an auditable playbook when no narrower one fits: a large migration, an ambitious multi-part change, or work a human reviews after stepping away. Scales rigor to the task, runs a hypothesis loop, and logs decisions. Use for /pstack:figure-it-out or 'figure it out'.

description没有更具体的剧本合适时，设计一份可以审查的剧本：一次大迁移、一个有野心的多部分改动，或者有人离开、回来再审查的工作。它按任务调整严格程度，跑一个假设循环，并记录决定。用于 /pstack:figure-it-out 或「figure it out」。

Figure it out

Figure it out（自己想办法搞定）

When the task matches no playbook, design one. The deliverable before any code is the workflow itself: a sequence of phases that scales rigor to the task, runs the scientific method, and leaves a decision trail a human can audit after stepping away.

任务对不上任何剧本时，就设计一份。写任何代码之前，要交出的东西是工作流程本身：一串阶段。它按任务调整严格程度，按科学方法来跑，并留下一份决定记录，让人离开后回来也能审查。

Start

开始

Open a todolist whose first item is to read the Principles section of the poteto-mode skill. Then add the phases below as todos.

开一个待办清单，第一项是读 poteto-mode 技能的 Principles 一节。然后把下面的各个阶段加成待办。

Phase A: Frame

阶段 A：框定

Ground first, then commit. Don't start the run until you can state:

先摸底，再拍板。在你能说出下面这些之前，不要开始跑：

  • The definition of done as a falsifiable predicate (the prove-it-works principle skill).
  • Scope, quantified: rough units and effort, plus the blockers grounding surfaced.
  • The rigor level, biased high. One-way doors and high blast radius get more. Reversible low-stakes steps get less. Rigor is gates and artifacts, not "try harder".
  • 「做完」的定义，写成一个可以被证伪的判断条件（prove-it-works 原则技能）。
  • 范围，用数字说：大致有多少个单元、多少工作量，再加上摸底时发现的阻碍。
  • 严格程度，宁高勿低。单向门（做了就退不回来）和影响面大的，给更多。可撤回、风险低的步骤，给更少。严格程度是关卡和能拿来检查的东西，不是「更努力一点」。

Present the framing and tradeoffs before committing to a long run. Reversible work proceeds (the never-block-on-the-human principle skill), but a multi-hour run earns one checkpoint.

投入一次长时间运行之前，先把框架和取舍摆出来。可撤回的工作照常推进（never-block-on-the-human 原则技能），但一次好几个小时的运行，值得设一个检查点。

Phase B: Design the workflow

阶段 B：设计工作流程

Decompose into atomic, independently-landable units. Sequence riskiest-unknown-first. Scaffold and verification come before features (the foundational-thinking principle skill).

拆成最小的、能各自独立合进去的单元。最没把握、风险最大的排在最前。搭架子和验证先于功能（foundational-thinking 原则技能）。

  • Build the verification harness before the work, with the baseline captured from the pre-change state, so the check reads as "old value vs new value".
  • For one-way-door design decisions, run the architect skill (it runs arena). Skip it for mechanical work whose shape is already concrete. A second arena over a settled design is over-engineering (the laziness-protocol principle skill).
  • Decide what fans out. Parallelize only across seams, and give each worker its own worktree or branch (the separate-before-serializing-shared-state principle skill). Don't over-fan. Pick each subagent's reasoning level and fast or standard speed for the job, per the Subagents section of the poteto-mode skill.
  • Write the designed phase list down. That list is what the human reviews.
  • 干活之前先搭好验证工具，从改动前的状态里先记下基线，这样检查读起来就是「旧值对比新值」。
  • 遇到单向门式的设计决定，运行 architect 技能（它会运行 arena）。形状已经很具体的机械性工作，就跳过它。对一个已经定下的设计再来一轮 arena，就是过度设计（laziness-protocol 原则技能）。
  • 决定哪些要分头去做。只在天然的分界处并行，并给每个干活的帮手 AI 各自的 worktree 或分支（separate-before-serializing-shared-state 原则技能）。不要分得太散。每个帮手 AI 的推理强度、用快速还是标准速度，按任务来选，参照 poteto-mode 技能的 Subagents 一节。
  • 把设计好的阶段清单写下来。审查的人看的就是这份清单。

Then execute the design. Add its steps to the todolist as concrete items between the Phase C and Phase D entries. Run each under the Phase C loop discipline, and weave the Phase D log through them, a row as each step lands, rather than saving the whole trail for the end.

然后执行这个设计。把它的步骤作为具体的条目，加到待办清单里阶段 C 和阶段 D 两项之间。每一步都按阶段 C 的循环规矩来跑，并把阶段 D 的日志穿插进去，每完成一步记一行，而不是把整份记录留到最后再写。

Phase C: Run the loop

阶段 C：跑循环

Each unit is an experiment. State the hypothesis, make the smallest change, measure against the predicate on the real artifact, keep it if it advanced, revert it if it didn't. Apply the sequence-verifiable-units principle skill, verifying each unit before starting the next instead of batching checks at the end.

每个单元都是一次实验。说出假设，做最小的改动，在真实的产出上对照判断条件去量，往前推进了就留下，没有就撤回。应用 sequence-verifiable-units 原则技能：验证完一个单元再开始下一个，而不是把检查都攒到最后。

  • Verify by inspecting the artifact, never a self-report. When something passes too easily, suspect the observation method before the system.
  • Pair delegated work with a judge. If a worker games the gate, reset and harden the contract. If the gate itself is wrong, fix the gate in its own change rather than routing around it.
  • A verdict is VERIFIED, NOT VERIFIED, or INCONCLUSIVE. Inconclusive is not a pass. Don't hide a negative.
  • 靠检查真实的产出来验证，绝不靠自我汇报。某件事通过得太容易时，先怀疑观察的方法，再怀疑系统。
  • 交出去的活，要配一个裁判。如果干活的帮手 AI 钻了关卡的空子，就重来，并把约定收紧。如果关卡本身错了，就在一个单独的改动里修好关卡，而不是绕开它。
  • 结论只有 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE 三种。说不准不算通过。不要藏起负面的结果。

Phase D: Keep the audit trail

阶段 D：留下审查记录

Log the run via the show-me-your-work skill. figure-it-out's work is usually ambitious enough to commit the trail so the reviewer can read it in the PR. The trail plus the diff is what lets the human come back and trust the work.

用 show-me-your-work 技能记录这次运行。figure-it-out 的工作通常大到值得把记录提交上去，这样审查的人能在 PR 里读到它。记录加上 diff，才能让人回来时信得过这份工作。

Phase E: Verify and hand back

阶段 E：验证并交回

Check the whole against the Phase A predicate on the real product, not just the harness. Encode any recurring correction as a gate, a lint rule, a check, or a script (the encode-lessons-in-structure principle skill).

在真实的产品上，而不只是在验证工具上，对照阶段 A 的判断条件检查整体。任何反复出现的纠正，都写成一道关卡、一条 lint 规则、一项检查或一个脚本（encode-lessons-in-structure 原则技能）。

Reply: the playbook you designed, the rigor level and why, the decision-trail path, what's verified against the predicate, and what's still open.

回复： 你设计的剧本、严格程度及其理由、决定记录的路径、哪些已经对照判断条件验证过，以及还有哪些没解决。
