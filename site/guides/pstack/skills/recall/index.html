/pstack:recall

按需点名

一句话翻你最近的聊天和共享记录，帮你想起做到哪了、下一步做什么。

什么时候用
隔几天回到老话题，或开新对话前想先找回进度。
要一起装
why、unslop
这样说
/pstack:recall 帮我回忆上周导出功能那块做到哪了

用它和不用它

同一件事，直接跟 AI 说，和点名用 /pstack:recall，AI 的做法不一样：

直接说用 /pstack:recall
只翻自己的聊天记录拼出来龙去脉同时查 PR、工单、聊天频道和线上报错这些共享记录
照聊天里的说法报进度用 git 和 gh 核对每个 PR、分支和工单现在的状态
顺带翻了别的项目的聊天先报出要查的范围，默认当前项目的最近 7 天

开头开头讲它从你的聊天记录和 PR、工单等共享记录里找回进度，分六步：分清任务、定范围、分头翻聊天、查共享记录、核对实际状态、写简报。

  1. 1输出约定简报依次写：最多 5 条的概况，每条线一个状态标签，最多 5 个反复出现的问题，一个具体的下一步。

写法亮点

挑了几句原文：每句让 AI 做什么、为什么这样写管用、你写提示词时怎么借来用。

  1. 给模糊的词一个默认值

    "recent" is a real range, default the last 7 days

    「最近」是一个真实的范围，默认最近 7 天

    让 AI
    你只说「最近」，它就查最近 7 天，不会自己随意理解成昨天或上个月。
    为什么管用
    「最近」可长可短，配一个默认的数字，AI 就不用猜，你也知道它查了多少。
    借来用
    用到模糊的词时配上默认值：「『尽快』指今天下班前，除非我另说。」

  2. 点破它会悄悄打的折扣

    Never quietly turn "all" into "recent N".

    绝不悄悄把「全部」变成「最近 N 个」。

    让 AI
    你说查「全部」，它就真查全部，不会悄悄只看最近几个就交差。
    为什么管用
    写出 AI 最容易偷偷缩水的那一步，比泛泛地说「要仔细」管用得多。
    借来用
    要 AI 全面检查时写明：「要看全部 37 个文件，不能抽几个看完就说都没问题。」

  3. 只给几个固定状态选

    A thread with no tag is not done yet, so tag it.

    没有标签的一行还没写完，所以给它打上标签。

    让 AI
    每件事都标明是已合并、还开着、还在做还是没开始，没有「差不多了」这种说法。
    为什么管用
    只能从几个固定标签里挑，AI 就没法用含糊的话把真实状态带过去。
    借来用
    要进度时给出可选的状态：「每项任务后面标上『做完』『进行中』『没开始』中的一个。」

  4. 规定先说什么后说什么

    Lead with the capsule, then the thread status, then the problems, then the next move.

    先写小结，然后是每件事的状态，然后是问题，然后是下一步。

    让 AI
    简报一打开就是结论和现状，细节在后面，你读两行就知道进展到哪了。
    为什么管用
    给出固定的顺序，最要紧的话就不会被埋在一堆细节中间。
    借来用
    要汇报时规定顺序：「先说结论，再说原因，最后说下一步做什么。」

全文

AI 读到的就是这份 SKILL.md。可以看中文、看原文，或者一段一段对照着看。

descriptionReconstruct your recent working context from your own chat history, live state, and the shared record (user reports, prior fixes, incidents), then hand back a tight current-state brief. Use for 'recall my work on X', 'catch me up', 'what have I been working on', 'where did I leave off', before starting or resuming work.

description从你自己的聊天记录、当前的实际状态和共享记录（用户的反馈、以前的修复、事故）里，重建你最近的工作情况，然后交回一份紧凑的现状简报。用于「回忆一下我在 X 上的工作」「帮我跟上进度」「我最近在忙什么」「我上次做到哪了」，以及开始或继续工作之前。

Recall

Recall（找回进度）

Before you start or resume work, you rebuild the user's recent working context and hand back a tight capsule of where things stand now and what to do next.

在你开始或继续工作之前，你要重建用户最近的工作情况，交回一份精简小结：现在进展到哪了，下一步做什么。

Keep it tight and on-topic. Read only what the in-scope threads need, then stop.

保持紧凑，不跑题。只读范围内那几件事需要的东西，然后停下。

Your context lives in two records. Your own chat history holds what you did and decided. The shared record holds everything that happened around the same code under other names: the symptoms users keep reporting, the fixes that shipped and got reverted, the errors still firing in prod. That second record is what the why skill searches, across source control, the issue tracker, chat and issue channels, long-form docs, and error tracking. A feature with a long bug tail keeps most of its story there, so don't reconstruct it from your transcripts alone.

你的工作情况存在两份记录里。你自己的聊天记录，存着你做了什么、定了什么。共享记录，存着同一块代码周围、以别的名字发生过的一切：用户反复报告的症状，上线后又被回退的修复，生产环境里还在报的错误。这第二份记录，正是 why 技能要搜的东西，范围包括版本控制、issue 跟踪系统、聊天和 issue 频道、长篇文档，以及错误跟踪。一个拖着一长串 bug 的功能，大部分故事都在那里，所以不要只靠你的对话记录来重建它。

Transcripts live where your harness keeps them. Each file is JSONL. Find the active workspace's directory for your harness. If you can't tell which harness you are, check which of these exist for this workspace:

对话记录存在你所用的工具存放它们的地方。每个文件都是 JSONL。找到你所用的工具里，当前工作区对应的目录。如果你分不清自己是哪个工具，就看看下面这些里，哪些对这个工作区存在：

  • Cursor: ~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl. <slug> is the workspace path with the leading slash dropped and each "/" turned into "-" (/Users/you/proj becomes Users-you-proj).
  • Claude Code: ~/.claude/projects/<slug>/<session-id>.jsonl. <slug> is the workspace path with every character that isn't a letter or digit turned into "-" (/Users/you/proj becomes -Users-you-proj).
  • Pi: ~/.pi/agent/sessions/--<slug>--/<timestamp>_<id>.jsonl. <slug> is the workspace path with the leading slash dropped and each "/" turned into "-" (--Users-you-proj--).
  • Codex: ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl, not grouped by workspace. Keep only files whose first line has payload.cwd equal to the workspace path.
  • OpenCode: ~/.local/share/opencode/storage/. Sessions are JSON files under session/<project-id>/, with their messages under message/ and part/.
  • Cursor: ~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl。<slug> 是工作区路径去掉开头的斜杠，再把每个「/」换成「-」（/Users/you/proj 变成 Users-you-proj）。
  • Claude Code: ~/.claude/projects/<slug>/<session-id>.jsonl。<slug> 是工作区路径里每个不是字母或数字的字符都换成「-」（/Users/you/proj 变成 -Users-you-proj）。
  • Pi: ~/.pi/agent/sessions/--<slug>--/<timestamp>_<id>.jsonl。<slug> 是工作区路径去掉开头的斜杠，再把每个「/」换成「-」（--Users-you-proj--）。
  • Codex: ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl，不按工作区分组。只保留第一行的 payload.cwd 等于工作区路径的文件。
  • OpenCode: ~/.local/share/opencode/storage/。会话是 session/<project-id>/ 下的 JSON 文件，它们的消息在 message/ 和 part/ 下。
  1. Classify, then route. One specific prior chat to resume is the session-pickup playbook, not this. Turning habits into a durable skill is automate-me. A human-readable summary of your work is a different task. Recall loads working context across recent chats before you act. If the user already gave you a full state capsule (paths, branch, the change), use it and skip the mining.
  2. Lock the scope before searching. Pin the window ("recent" is a real range, default the last 7 days), the topic if named, and the workspace (default the active one. Never read another project's transcripts without being asked). State the scope back. Never quietly turn "all" into "recent N".
  3. Fan out across your chat history. Spawn parallel subagents on a fast, cheap model, each taking a slice of the corpus. Tell every subagent to order candidates by real modification time (ls -t) and never by UUID name, grep the topic first and then read only the matching chats and only their relevant regions, and skip the current chat plus obvious noise (subagent, eval, and test chats). Each returns the same schema, one block per chat: topic, the user's goal, decisions, open threads, struggles and corrections, and artifacts (PRs, tickets, branches), each citing the chat UUID. For one or two chats, skip the fan-out and search directly. The raw transcripts stay in the subagents. The main thread gets only their findings. Pick each subagent's reasoning level and fast or standard speed for the job, per the Subagents section of the poteto-mode skill.
  4. Sweep the shared record whenever the topic names a feature, file, subsystem, area, or bug. This is the default, not a judgment call, and "my work on X" does not exempt it. Hand it to the why skill's source investigators, but steer their question from "why was this built this way" to "what's the current state, what's been tried and didn't hold, and what are users still reporting". Reuse its per-source playbooks, run the investigators in parallel with the chat-history mining, and inherit its posture: one investigator per source, null results are findings, skip an unavailable MCP and say so. Fold what comes back into the brief. Skip this step only for pure activity recall with no named target ("what did I do this week"), where your own history and live state are the entire answer.
  5. Verify against live state. Take the PRs, branches, and tickets that the mining and the sweep surfaced and check them with git and gh. When the answer hinges on what an agent actually did (the tools it ran, files it read, errors it hit), read the full transcript, not just a trimmed local copy.
  6. Write the brief to the contract below. Group by thread. Stay on the named topic.
  1. 先分类，再分流。要接着某一个具体的旧对话做，用的是 session-pickup 剧本，不是这个。把习惯变成一个长期可用的技能，是 automate-me。给人看的工作总结，是另一件事。Recall 是在你动手之前，把最近几个对话里的工作情况装进来。如果用户已经给了你一份完整的现状小结（路径、分支、改动），就直接用，跳过挖掘。
  2. 搜索之前先锁定范围。定下时间窗口（「最近」是一个真实的范围，默认最近 7 天）、话题（如果点了名），以及工作区（默认是当前这个。没被要求时，绝不读别的项目的对话记录）。把范围说回给用户。绝不悄悄把「全部」变成「最近 N 个」。
  3. 在你的聊天记录里分头去找。并行派出几个帮手 AI，用快而便宜的模型，每个负责一部分资料。告诉每个帮手 AI：按真实的修改时间（ls -t）给候选排序，绝不按 UUID 名字排；先 grep 话题，然后只读匹配上的对话，而且只读相关的部分；跳过当前这个对话，以及明显的噪音（帮手 AI、评测和测试用的对话）。每个帮手 AI 都按同样的格式交回，每个对话一块：话题、用户的目标、做出的决定、没收尾的事、卡住和被纠正的地方，以及产出（PR、工单、分支），每一项都注明对话的 UUID。只有一两个对话时，就不用分头，直接搜。原始对话记录留在帮手 AI 那里，主对话只拿到它们的发现。每个帮手 AI 的推理强度、用快速还是标准速度，按任务来选，参照 poteto-mode 技能的 Subagents 一节。
  4. 只要话题点了一个功能、文件、子系统、领域或 bug 的名字，就去翻一遍共享记录。这是默认动作，不靠判断决定，「我在 X 上的工作」也不能免掉这一步。把它交给 why 技能里各种来源的调查员，但把它们的问题从「为什么当初这样做」改成「现在是什么状态，试过什么、没能撑住，用户还在报告什么」。复用它为每种来源准备的剧本，让调查员和聊天记录的挖掘并行跑，并沿用它的做法：每种来源一个调查员，没找到也是一种发现，某个 MCP 用不了就跳过，并说出来。把收回来的东西并进简报。只有纯粹回忆做过哪些事、没有点名对象时（「我这周做了什么」），才跳过这一步，因为这时你自己的记录和实际状态就是全部答案。
  5. 拿实际状态核对。把挖掘和翻查中冒出来的 PR、分支和工单，用 git 和 gh 查一遍。当答案取决于某个 AI 实际做了什么（它跑了哪些工具、读了哪些文件、碰到了哪些错误）时，读完整的对话记录，不要只看一份删减过的本地副本。
  6. 按下面的约定写简报。按事情分组。不离开点了名的话题。

Output contract

输出约定

Lead with the capsule, then the thread status, then the problems, then the next move. Deeper detail goes below or gets cut.

先写小结，然后是每件事的状态，然后是问题，然后是下一步。更深的细节放到下面，或者删掉。

  • Capsule. At most 5 bullets. What this work is and where it stands overall.
  • Threads. One line each, prefixed with exactly one status tag: [merged #N], [open PR #N], [in flight <branch>], [verified, uncommitted], [reverted #N], or [planned, not started]. A thread with no tag is not done yet, so tag it.
  • Problems. At most 5, the recurring ones. Include the symptoms users keep reporting and any fix that shipped and was reverted, so the next attempt starts where the last one failed.
  • Next move. The single most useful next action, concrete.
  • 小结。 最多 5 条要点。这份工作是什么，整体进展到哪了。
  • 各件事。 每件一行，前面加一个、且只加一个状态标签：[merged #N]、[open PR #N]、[in flight <branch>]、[verified, uncommitted]、[reverted #N] 或 [planned, not started]。没有标签的一行还没写完，所以给它打上标签。
  • 问题。 最多 5 个，挑反复出现的。写上用户一直在报告的症状，以及上线后又被回退的修复，好让下一次尝试从上一次失败的地方接着来。
  • 下一步。 最有用的那一个下一步动作，要具体。

An adjacent feature or ticket stays out unless it blocks this one. When the capsule and thread lines outgrow a screen, cut detail before you cut threads. Write the brief through the unslop skill, cite chat findings by UUID and shared-record findings by their source (PR #, ticket ID, chat permalink, error-tracker issue), and sanitize private context before any public output.

相邻的功能或工单不写进来，除非它挡住了这一件。小结和各件事的行超出一屏时，先删细节，再删事情。简报要过一遍 unslop 技能；聊天里的发现注明 UUID，共享记录里的发现注明来源（PR 编号、工单 ID、聊天的固定链接、错误跟踪里的 issue）；任何公开输出之前，先清理掉私人内容。

Reply: the brief, to the contract above.

回复： 按上面的约定写的简报。
