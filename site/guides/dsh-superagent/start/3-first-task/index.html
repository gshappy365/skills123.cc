新手入门约 10 分钟

第一次派活

用一句三段式的话把一件小事交给它，并知道屏幕上该出现什么。

挑一件真实、但不大的事

第一次别挑「重构整个模块」。挑一件你能一眼判断对不对的：修一个窄屏错位、给某个函数补一条测试、把 README 里过期的命令改掉。这样你能把注意力放在看它怎么做事，而不是判断改动本身。

一段话写三样东西

好请求最多写三样：要什么 · 怎样算做完 · 做完给我看什么。不要写「具体怎么做」，也别写你猜的原因——那两样最容易把它带偏。

@<agent login> 请修复首页在窄屏（375px 以下）时标题换行错位的问题，
顺手补一条对应的回归测试。

做完的标准：在 375px 宽度下标题不溢出容器，测试全部通过。
做完请给我：改动前后的截图对比，以及测试命令的实际输出。

把 <agent login> 换成安装时定的智能体账号。这条要发成一条新的 Issue 或评论——直接编辑已有 Issue 的正文来补 @，来源收不到。

三段式为什么管用

「怎样算做完」让它可以自己判断，不用回来问你；「给我看什么」让它交出证据，而不是一句「应该没问题了」。这正好对上它自己的规矩：诚实交付，草稿标未完成，没有真实截图就不算就绪。

接下来屏幕上会依次出现什么

  1. 一条确认。它会在你原消息下面回一句，说清楚接了什么、打算交出什么。之后就安静了。
  2. 一张工单卡片。约一分钟内，面板 Overview 出现新的工单，能看到它来自哪条消息、依据哪条规则、授权范围有多大。
  3. 过程在面板里，不在聊天里。Trigger、Eval、Execution 三页能看完整时间线；它不会每一步都来烦你。
  4. 一个结果，或者一个问题。要么是一个 PR，要么是一个很具体的、等你在原对话里回答的问题（面板里叫待人工决定）。
  5. 最后一句话回到原对话。PR 的结果会在原来那条 Issue / 群里通知一次。

你要做的只有三件事

  • 回答那个具体问题——一次一个，它不会一口气丢五个问题给你；
  • 审 PR——看它给的证据够不够、有没有顺手动了不该动的文件；
  • 合并——默认由人合并，它不会自己合。

不对怎么办

现象 先查哪里
@ 了完全没动静 发消息的人是否在允许名单里；Source 开关是否打开；Execution 页是不是被 Pause processing 暂停了
面板出现记录但没有工单 去 Eval 页看那条[[决定
它说做完了，但看不到证据 看 PR 描述里有没有实际命令输出、前后对比；没有就别合并，在原对话里要求补
想让它停 在原对话里发一句 @<agent login> 停一下，这个先不要继续了。

一句话拉回跑偏

不用改别的文件，只处理 <某个文件>。先把你现在改动了哪几个文件列给我，等我确认再继续。

订阅机制会把这条消息送给正在干活的工单当作上下文，不需要再走一次评估，也不需要重新 @ 一遍新工单。
