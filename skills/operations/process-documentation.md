# Process Documentation — Operations Plugin

> 所属插件：[Operations](/plugins/operations) · 来源：Anthropic knowledge-work-plugins · 兼容：Cowork + Claude Code

---

## 概述

Process Documentation 是 Operations 插件的核心技能。它将流程文档编写从"空白页恐惧"升级为**结构化 SOP 生成**——包含流程图、RACI 矩阵、详细步骤、异常处理和度量指标。与传统的文档模板不同，这个技能通过对话引导的方式，把存在于某个人脑子里的流程"倒出来"并组织成标准操作程序。

## 核心能力

### 1. SOP 结构

每次生成的 SOP 包含以下部分：

| 章节 | 内容 |
|---|---|
| **目的** | 流程存在的理由和达成的目标 |
| **范围** | 包含和不包含的内容 |
| **RACI 矩阵** | 每个步骤的负责人/批准人/咨询人/知情人 |
| **流程图** | ASCII 流程图或步骤描述 |
| **详细步骤** | 每个步骤的操作说明、角色、产出物 |
| **异常处理** | 边界情况和处理方式 |
| **度量指标** | 关键指标、目标值和测量方法 |
| **相关文档** | 关联的流程或政策 |

### 2. RACI 矩阵

| 步骤 | Responsible（执行） | Accountable（负责） | Consulted（咨询） | Informed（知会） |
|---|---|---|---|---|
| 步骤 1 | [谁做] | [谁批准] | [谁建议] | [谁需要知道] |
| 步骤 2 | [谁做] | [谁批准] | [谁建议] | [谁需要知道] |

### 3. 异常处理表

| 场景 | 处理方式 |
|---|---|
| [异常情况] | [标准处理流程] |
| [边界条件] | [处理方案] |

## 使用场景与案例

### 场景 1：将经验文档化

**输入**：
```
/process-doc 客户退款流程
```

**输出**：通过对话引导，AI 逐步询问退款流程的触发条件、各步骤负责人、审批路径、异常情况，最终生成完整的 SOP。

**关键价值**：把存在于老员工脑子里的经验变成可传承的文档，降低单人离职的风险。

### 场景 2：合规审计准备

**输入**：
```
帮我记录变更管理流程，需要满足 SOC2 合规要求。
```

**输出**：包含变更申请、审批、测试、发布、回滚各步骤的完整 SOP，附带 RACI 矩阵和审计追踪要求。

**关键价值**：合规审计需要的流程文档可以快速生成，且结构满足审计要求。

## 与其他工具对比

| 维度 | Process Doc（本技能） | Confluence 模板 | 流程挖掘工具 | 手动编写 |
|---|---|---|---|---|
| 生成方式 | 对话引导 | 空白模板 | 数据驱动 | 空白页开始 |
| 结构化程度 | 自动结构化 | 取决于模板 | 自动 | 取决于能力 |
| 异常处理 | 自动包含 | 需手动添加 | 数据发现 | 需经验 |
| 学习成本 | 描述即可 | 需了解模板 | 需培训 | 无 |
| 输出一致性 | 每次相同 | 取决于使用 | 标准格式 | 每次不同 |

## 连接工具后的增强能力

| 连接的 MCP | 分类 | 增强效果 |
|---|---|---|
| **Notion/Confluence** | 知识库 | 搜索已有文档避免重复，发布完成后的 SOP |
| **Jira/Linear** | 项目追踪 | 将流程链接到相关项目和工单 |

连接方式：在 Operations 插件的 `.mcp.json` 中配置对应的 MCP 服务器。

---

## 最佳实践

1. **从混乱开始** — 不需要完美的描述，告诉 AI 今天实际怎么做，它会帮你结构化
2. **包含异常** — "通常我们做 X，但有时 Y" 是最有价值的文档内容
3. **说出人名** — 即使角色会变，知道今天谁做什么有助于把流程做对
4. **定期审查** — 流程会演变，建议每季度审查和更新 SOP
