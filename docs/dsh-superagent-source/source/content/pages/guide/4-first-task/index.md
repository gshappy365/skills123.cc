# 发出第一个任务

## 语法只有一条

在 GitHub 的 **Issue 或评论**里写：

```
@<agent login> <你要它做的事>
```

默认约一分钟轮询一次，所以别连着刷新。飞书则是在配置过的群里 @ 机器人，或者私信（如果开了 `directMessages`）。

<div class="tu-note tu-note--warn">
<strong>编辑 Issue 正文补 @ 是无效的</strong><p>来源监听的是新评论、新 Issue、通知与 CI 变化这类事件，不接收「把已有正文改一下加上 @」。请发一条新评论。</p>
</div>

## 三个能直接改尖括号就用的请求

```
@<agent login> 请修复 <页面/模块> 在 <具体条件> 下的问题，
并补一条回归测试。
做完的标准：<一句能判断过或不过的条件>。
做完请给我：<测试命令的实际输出 / 改动前后对比>。
```

```
@<agent login> 先不要改代码。把 <模块> 现在的调用关系讲一遍，
列出你认为最可能出问题的两处，等我确认再动手。
```

```
@<agent login> 把 README 里过期的安装命令更新成现在实际能跑通的版本，
只改 README，不碰其他文件。做完把改了哪几行贴给我。
```

第二、三条为什么值得写：它自己有「先复述、先确认一次再动手」和「按影响停止」的规矩，你明确说「先别改」，就能把一次调查和一次改动分开，成本更低。

## 从一句话到一张工单，中间发生了什么

1. **来源**把这条评论变成一条不可变的触发，记下 actor 和 `mention` / `direct` 之类的元数据；
2. 同一条触发重复到达也只会建一个工单（幂等）；
3. 若这条线程已被某个工单订阅，消息直接扇出当上下文，**不新开评估**；
4. 否则进入评估：先确定性准入（谁发的、有没有 @、属于哪类消息），再模型研判，产出一条决定；
5. `accept` 时**原子地**创建工单 + 授权 + 订阅 + 第一次派工 + 一条确认消息；
6. 执行器在自己的目录里（默认先跑 prepare 命令，例如用 `git worktree` 建独立工作树）开工。

## 你应该看到什么

| 在哪看 | 看到什么 |
| --- | --- |
| 原对话 | 一条确认，说清接了什么、预计交什么；之后安静 |
| Overview | 需要人处理的工单、系统问题、近 24 小时活动计数 |
| Trigger | 线程时间线，触发按时间倒序，还有决定与订阅 |
| Eval | 那条决定的理由、命中的规则、Policy 版本 |
| Execution | 工单阶段、派工状态、报告、等待的输入 |

## 不对怎么办

| 现象 | 去哪查 |
| --- | --- |
| 完全没记录 | Source 页的开关与 setup 问题；发消息的人是否在允许名单 |
| 有触发但决定是 `ignore` | Eval 页的理由。`observe` 下推断的工作会写「本来会接」 |
| 决定是 `unavailable` | 评估超时或不可用，触发会重新排队；面板上可以 `Evaluate again` |
| 工单 `failed` | 多半是 prepare 命令（克隆路径）失败，改好后用 `Retry` |
| 它开始动不该动的文件 | 在原对话里回一句「只处理 <文件>，先把改动清单给我」；订阅会把这句送到工单 |
