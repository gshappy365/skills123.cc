# 一个工单的一生

## 五个东西不是同一个东西

| 概念 | 是什么 | 最容易混成 |
| --- | --- | --- |
| 工单 Ticket | 一个被授权的工作单元，只有评估能创建 | 常被当成一个 PR，或一个会话 |
| 授权 Mandate | 接单时授予的记录：Policy 版本、范围、强度、命中规则、发送者身份；不可变 | 常被当成登录凭证 |
| 派工 Assignment | 工单绑定到某个执行器实例；一个工单先后可以有好几个 | 常被和工单混为一谈 |
| 订阅 Subscription | 工单 ↔ 线程的多对多关系，由线程持有 | 常被以为会顺带授权 |
| 报告 Report | 派工报给工单的结构化状态 | 常被当成一段日志文本 |

## 状态各自独立

- **工单**：`open → ended`，人在它订阅的线程上说句话，可以再回到 `open`（除非人明确停过它）。它自己定义状态，**不跟着 DSH 会话走**——因为工单可以被交接、被恢复、被好几个执行器轮流做。
- **派工**：`pending → running → ended`，独立于工单。只有它的**最终报告**才可能从执行器这一侧结束工单。
- **报告**：`progress` 进展 · `waiting` 等待 · `ready` 就绪 · `blocked` 受阻 · `failed` 失败 · `dropped` 无需处理。

还有一个叫[[待人工决定|Attention：工单上等人回答的一个结构化具体问题]]的东西：执行器把**一个**具体问题放进报告，主会话原样转给人。它是结构化字段，不是从自由文本里猜「是不是在等人」——文档明确把「从报告正文推断等待状态」列进了被否决的设计。

## 授权为什么不可变

Mandate 记的是「当时凭什么允许做这件事、允许做到哪」。工单结束不会让它失效；只有人明确 `stop` 才撤回，或者恢复前拿当前 Policy 重新校验失败时被吊销。Policy 变了不会取消正在跑的工单（那样会留下一半完成的工作），而是把变更**记下来并送给它的派工**。

范围变大要另开工单，而不是在原工单上放宽。

## 订阅：后续讨论为什么不用再 @

一个工单会订阅它起始的那条线程，也会订阅跟它有关的线程（例如它自己开的 PR）。之后这些线程上的新消息会**扇出**给所有还活着的订阅工单：

- 不检查是谁发的，绕过准入闸门；
- 但只作为**上下文**，不带来任何新权限；
- 人发的消息能让已结束的工单在同一份 Mandate 下恢复，不需要再评估、不需要新决定；
- 机器人和 CI 的消息不会送到已结束的工单（执行器恢复时会自己重读线程）；
- 被人停掉的工单什么都收不到；
- 只为了看上下文而订阅的线程，不会让工单恢复。

还有个细节：主会话只在一条消息**明确指向**某个工单（它的 PR、Issue、原始消息、确认消息，或恰好只匹配到一个工单的最近改动）时，才把线程挂到已有工单上。光是「话题很像」不够。

## 你应该看到什么

在工单详情里：最初的触发、决定与理由、范围、Policy 版本，往下折叠才是派工和次要细节。一个走完的工单，结局是「PR 已合并」或「被人停止」这样的** human-readable 结果**，不是一串内部状态码。

## 常见误解速查

| 想法 | 实际情况 |
| --- | --- |
| 「工单就是那个 PR」 | PR 是它交付的一种结果；工单还会继续订阅那条 PR 线程 |
| 「会话断了，活就丢了」 | 工单状态自己保存，可以交接或恢复 |
| 「群里机器人说一句，它就多干一件」 | 扇出只给上下文，不授权 |
| 「把提示词写严一点就能限制权限」 | 权限由 host 和工具参数强制，提示词排在它们后面 |
| 「Policy 一改，在跑的活自动作废」 | 不会取消，变更被记录并送达 |
