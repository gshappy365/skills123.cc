# 配好「谁能叫它干活」

## 三道闸门

| 闸门 | 管什么 | 在哪配 |
| --- | --- | --- |
| 允许名单 allowed list | 哪个 GitHub 登录名 / 飞书用户能发起工作 | Settings → Eval → On each Source |
| 准入表 admission table | 哪类消息、有没有 @、是不是名单里的人，分别给多强的资格 | 同一个 Source 的 tab |
| 接单模式 accept mode | 推断出来的工作，是记下、还是真接 | Settings → Eval |

**名单为空，任何请求都变不成工单。**这是 host 强制的，不是提示词里的一句话。消息、评论、引用文档都只是判断用的输入，改不了权限。

## 两种强度

| 强度 | 含义 |
| --- | --- |
| `explicit` 明确 | 有人直接、明确地点名要它做某件事 |
| `inferred` 推断 | 它从上下文觉得「大概该做点什么」，没人直接要求 |

默认的准入表大致是：名单里的人 @ 了 → `explicit`；名单外的人 @ 了 → 忽略；没 @ → 忽略。想让某个支持群里任何人都能派活，把那一行的「名单外 @」设成 `explicit` 即可。

机器人（GitHub Apps、`[bot]` 结尾的登录名、飞书 bot）只能产生 `inferred` 候选，**不能 explicit，也不能叫停工作**。用普通账号跑的自动评审会被 host 当成「人」，得在团队提示词的 review bots 里点名。

## 接单模式：默认最保守

| 模式 | 推断出来的正向工作 |
| --- | --- |
| `off` | 根本不成候选 |
| `observe`（默认） | 照常评估，但只记成 `ignore`，理由写「本来会接」（would accept），**不真的开干** |
| `auto` | 正向评估直接接单 |

==明确点名（`explicit`）的请求，在三种模式下都生效==。所以新手最稳的路径是：

1. 先保持 `observe`，正常用一段时间；
2. 到 Eval 页看那些「本来会接」的记录，判断它的判断对不对；
3. 觉得稳了，再考虑切 `auto`；觉得吵，就把提示词改短改严，或者干脆暂停。

<strong>自动合并默认关闭</strong><p>README 与 SETUP 都推荐选「不要」。它默认从不以智能体账号启用自动合并（GitHub 会把合并归到启用者头上）；真要开，必须在 <code>Delivery requirements</code> 里点名另一个账号的 CLI。默认条件还包括：PR 属于该工单、状态就绪、审批覆盖 head commit、增删合计小于 200 行。host 本身没有合并决策逻辑，强制审批要靠 GitHub 的分支保护 + 自动作废旧审批。</p>

## 一个容易忽略的机制：订阅绕过闸门

已经开了的工单会[[订阅|Subscription：工单与线程的多对多关系，把新消息当上下文送进来]]它所在的线程。此后这条线程上的消息（包括机器人和 CI 的）会直接扇出给工单当**上下文**，不再过一次评估，也**不会因此获得新的授权**。

要理解的是：==订阅只送上下文，不发权限==。授权来自工单那份不可变的 Mandate。这就是为什么「后续讨论不用再 @ 一遍」，同时「随便一句机器人评论也不会让它多干一件事」。

## 你应该看到什么

保存设置时，如果返回 `restarting: true`，服务会重启一次；等 `scripts/dsh-superagent status` 不再退出 1，再重新读一次设置，确认版本号变了。之后在 Eval 页能看到每条决定写了理由和命中的规则。

## 不对怎么办

- **保存被拒**：响应体里会写明是哪一项安装问题，去 [部署文档的 Troubleshooting 表](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/006-deployment.md) 对一下。
- **@ 了没反应**：先去 Source 页看它是不是开着、有没有 setup 问题，再去 Execution 页看 `Pause processing`。
- **改了提示词想改权限**：改不了。权限在 host 和工具参数里强制，提示词排在它们之后。
