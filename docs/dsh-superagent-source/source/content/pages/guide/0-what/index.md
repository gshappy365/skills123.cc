# 它到底是什么

## 定位

`dsh-superagent` 是**打包给 DeepSeek Harness 的一份插件**，为一个 GitHub 仓库提供一个主动式编码智能体，可选接飞书。它监听事件，在有人获准请求时开一份工单，在自己的会话和目录里完成工作，并回到原对话里给出结果（通常是一个 PR）。另外有一个 Web 面板，只列出「需要人处理的事」。

仓库自己的定位写得非常克制：研究原型、仅供参考、不是官方产品、不是生产级软件，发布版本与内部版本、与论文里描述的设计都不完全一致。本站所有内容以公开的 `docs/` 编号文档为准。

## 一条原则管住所有设计

> **尽量少占用人的注意力，尽量多给出价值。**

一条消息、一个通知、一个问题、一个设置项、面板上的一个元素、文档里的一段话，都要算它花掉谁的注意力；给不回更多价值，就删掉。由此推出四条对智能体的要求：

- 只在被点名、或有团队写下的规则时才行动；
- 只在人必须行动或能用上结果时才说话，消息要短、回到原对话；
- 一次只问一个具体问题，用结构化形式问；
- **按影响停止，不按努力停止**：本地改动做到可评审就交；需要设计决策的，停下来问清楚。

以及四条对设计的要求：概念要少、设置要少、面板只显示需要人的事、文档按编号顺序读。

## 三层结构

| 层 | 负责什么 | 具体是什么 |
| --- | --- | --- |
| 来源层 | 把外部世界翻成事件 | GitHub 通知与订阅的 Issue / PR / CI；飞书群消息与私信 |
| 领域层 | 判断「这件事该不该做、允许做到哪」 | Source、Trigger、Thread、Eval、Policy、Mandate、Ticket、Assignment、Subscription |
| 执行层 | 真的去改代码 | 一个 DSH 会话 + 每个工单一个目录，通过 Assignment 接在领域层外面 |

关键的分界：**[[执行器|Executor：真正干活的那个会话与目录，在领域模型之外]]不在领域模型里**。领域层只管「授权与记录」，干活的是外面的端口。所以一个工单可以被交接到另一个执行器、可以在结束后被人一句话唤醒，而不用跟着某个会话一起消失。

## 一次工作的完整链路

```
有人在 Issue / 群里 @ 它
  → 来源把它变成一条不可变的触发（Trigger）
  → 若已落在某个订阅的线程，直接扇出给那个工单当上下文
  → 否则进入评估（Eval）：先确定性准入，再模型研判
  → 接单则原子创建工单 + 授权（Mandate）+ 派工（Assignment）
  → 执行器在自己的目录里改代码、跑验证、开 PR
  → 报告（Report）回到工单，渠道（Channel）把结果写回原对话
  → 人审、人合并；后续讨论继续由订阅送达同一个工单
```

想看更细的图，去 [概念全景图](/reference/flow/)。
