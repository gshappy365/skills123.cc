# 适不适合你

## 适合，如果

- 有一个**多人协作**的 GitHub 仓库，大家会在 Issue / PR 里讨论事情；
- 你愿意让一个 AI 长期在后台听着，并且有人负责审它交出来的东西；
- 有一台能长期运行、跑着 `tmux` 的机器，以及配好模型的 DeepSeek Harness；
- 你想减少的是「反复解释背景、来回追问、忘了跟进」这类协作成本，而不只是想让 AI 写点代码；
- 你能接受它更慢、更费 token。

## 先别用，如果

| 情况 | 更合适的做法 |
| --- | --- |
| 只有你一个人、只改自己电脑上的项目 | 直接用编码智能体的对话就够了 |
| 想要一个开箱即用的 SaaS 产品 | 这是研究原型，不是产品 |
| 用 GitHub Enterprise Server | 文档明确不支持 |
| 想让它自动合并、无人值守地刷 PR | 设计目标恰好相反：少打扰、由人把关 |
| 没有能长期运行的机器 / 没配模型 | 先把环境和 DSH 跑通 |
| 安全上不能接受它以你的系统用户运行 | 先准备专用系统账号，再评估 |

## 一个判断标准

问自己一句：**「团队现在最贵的，是写代码的时间，还是被反复打断的注意力？」**如果答案是后者，这套设计里「只在被点名时动手、只在有人要行动时说话」才对你有意义；如果答案是前者，它可能显得又重又慢。
