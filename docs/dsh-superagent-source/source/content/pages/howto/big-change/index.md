# 一次较大的改动

## 别写「做四小时」，写「什么算做完」

```
@<agent login> 目标：<一句话说清改完是什么样>。

完成标准：
- <能判断过或不过的条件 1>
- <条件 2>
- 现有 <某些行为> 保持不变

每做一个决定记一行：时间、决定、理由、证据。
遇到 <具体卡住的情况> 停下来问我，不要自己猜。
做完给我：决定日志、逐条完成标准的验证输出、改动文件清单。
```

## 三个要点

- **完成条件要能判断过没过**，模糊的「优化一下」会让它自己定义什么叫做完。
- **留一个逃生口**：写清楚「遇到什么就停下来问」，别让它猜。
- **决定日志**让你第二天只审决定，不用重读整个过程。

## 长任务的几个硬上限

- 一次 turn 结束后，后台最多再跑 **30 分钟**；超时 shell 会被杀掉并报「在等待」。
- handoff 时 subagent 会停，shell 可以留到派工结束，且**不占并发槽**。
- 并发默认 `maxWorkers = 3`；评估超时默认 120 秒。

看起来「卡住」时，先对照这三条，再看日志。

## 代价先说清

它会多跑检查、多用 token，更慢也更贵。小改动不要这么写。
